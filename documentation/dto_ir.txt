可以。基于我们上一轮已经确定的原则，我建议直接把它整理成 **TrustLens v2 Evidence IR 2.0**：不是继续堆 ontology，而是把 **Reconciliation / Web Grounding / Enterprise Grounding** 三种下游真正需要的 evidence 分开。

这一版我会重点修正 Gemini Matrix Edition 的几个问题：

* `table_type` 决定允许哪些 column。
* payroll / legal / official 不再被粗暴塞进 `FLOW_IN/FLOW_OUT`。
* `MEMO_NEUTRAL` 删除——Qwen 不负责判断某字段是否参与规则。
* 保留 `String Decimal`，避免 float。
* `COMPONENT` 使用有限 closed-world enum。
* Enterprise grounding 的 **key type** closed-world，但 **key value** 完全开放。
* Web grounding 完全 open-world。
* Semantic Engine 不进入这个 IR。
* source/bbox 保留，保证每一个 evidence 都能回指原文。
* JSON Schema 负责结构约束，Pydantic 再负责矩阵宽度等跨字段 validation。

下面这版可以作为你实际工程的 **schema v2.0 baseline**。

    def validate_matrix(self):
        width = len(self.columns)

        for row in self.tuples:
            if len(row) != width:
                raise ValueError(
                    f"Tuple width {len(row)} does not match "
                    f"column width {width}"
                )

        if self.source_element_ids is not None:

            if len(self.source_element_ids) != len(self.tuples):
                raise ValueError(
                    "source_element_ids row count must match tuples"
                )

            for row in self.source_element_ids:
                if len(row) != width:
                    raise ValueError(
                        "source_element_ids row width must match columns"
                    )

        return self

## 3. 一个很重要的设计决定：Matrix 的 cell 为什么全部是 string/null？

这是我建议你**保留**的。

例如：

```json
{
  "columns": [
    "COMPONENT",
    "AMOUNT",
    "RATE"
  ],
  "tuples": [
    ["BASIC_SALARY", "3000.00", null],
    ["EPF_EMPLOYEE", "330.00", "11"]
  ]
}
```

不要变成：

```json
[
  ["BASIC_SALARY", 3000.00, null],
  ["EPF_EMPLOYEE", 330.00, 11]
]
```

原因是你的 Matrix 是一个 **LLM extraction boundary**。

Qwen 输出：

```text
"3000.00"
```

而不是：

```text
3000.0
```

然后 Reconciliation Engine 自己：

```python
Decimal("3000.00")
```

这样：

**Qwen → Evidence IR → deterministic engine**

中间没有 Python/JSON float 偷偷破坏 monetary precision 的可能。

# 4. 但还有一个地方我建议你不要现在过度设计

就是 `COMPONENT`。

例如 payroll：

```text
BASIC_SALARY
ALLOWANCE
EPF_EMPLOYEE
SOCSO_EMPLOYEE
...
```

这是合理的，因为 deterministic reconciliation **确实需要知道类别**。

但千万不要继续膨胀成：

```text
BASIC_SALARY
BASIC_SALARY_ADJUSTED
BASIC_SALARY_PRORATED
BASIC_SALARY_PREVIOUS_PERIOD
...
```

这种 ontology。

原则应该是：

> **只有当下游 deterministic rule 无法在没有这个语义的情况下运行，才进入 closed-world enum。**

否则：

```text
raw text → Semantic Engine
```

或者：

```text
open key-value → Web Grounding
```

# 5. 最终 TrustLens v2 的数据流

我认为现在已经可以非常清楚地画成：

```text
                    ┌──────────────────┐
                    │   Original Doc   │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   Qwen VLM       │
                    │ extraction only  │
                    └────────┬─────────┘
                             │
                 ┌───────────┼────────────┐
                 │           │            │
                 ▼           ▼            ▼
        ┌────────────────┐ ┌──────────┐ ┌─────────────────┐
        │ Reconciliation │ │ Grounding│ │ Semantic Engine │
        │    Evidence    │ │ Evidence │ │  Original Text  │
        └───────┬────────┘ └────┬─────┘ └────────┬────────┘
                │               │                │
                ▼               ├──── Web ───────┤
        deterministic           │                │
        rules only              └── Enterprise   │
                │                                │
                ▼                                ▼
        arithmetic /                    LLM semantic
        balance / dates /               reasoning
        quantities
```

所以这个 schema 的核心不是“把所有 document knowledge 都结构化”。

恰恰相反：

> **把必须结构化的最小闭世界信息结构化；其余信息故意保持开放。**

这会让 TrustLens v2 后面扩展到新的 document type 时非常舒服——你不是每增加一种 document 就重新建立一个庞大的 universal ontology。
